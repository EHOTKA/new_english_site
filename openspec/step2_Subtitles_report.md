## 1. Контекст и цели задачи

`dialogue_lines` — единственная таблица, из которой дальше строится лексический профиль
пользователя (шаг 3: токенизация и лемматизация, шаг 4: SRS). Шаг 2 должен превратить
«сырой» `.srt` из торрента в чистый текст реплик с таймкодами.

**Требования к задаче:**
1. Прочитать `.srt` в любой распространённой кодировке (UTF-8, UTF-8 BOM, cp1251/cp1252, latin-1).
2. Разобрать cue'ы на `(start_ms, end_ms, text)`, не потеряв файл с побитыми блоками.
3. Вычистить SDH/ASS-шум: HTML-теги, `{…}`, `[…]`, `(...)`-ремарки, ♪-музыку, метки диктора,
   «- » в начале строки, склеить многострочные реплики.
4. Записать результат в `dialogue_lines` (`line_index`, `start_time_ms`, `end_time_ms`, `raw_text`)
   в транзакции, двигая `subtitles.status` по циклу `pending → processing → parsed/failed`.
5. Обеспечить повторный импорт того же файла без дублей и без потери данных.
6. Дать CLI для ручного прогона и приёмки, покрыть всё тестами (`unit` без БД + `integration` с БД).

Эталон чистки — матрица из 14 кейсов (`openspec/step2_Subtitles_tasks.md`, §4): она же источник
истины для тестов, она же — образцы в §6.4 этого отчёта.

## 2. Проблемы исходного подхода и их устранение

| Проблема | Причина | Решение |
|---|---|---|
| **`Fire off.Pull trigger.`** — две реплики склеились в одно слово | Склейка строк cue без разделителя (`"".join` / удаление `\n`) | Склейка через пробел + collapse `\s+` + «пробел перед знаком препинания» в конце (`D2`); опция `merge_lines=False` оставляет исходную построчность |
| **`<b>[MUSIC]</b>` оставлял `<b></b>`** | Скобки вырезались раньше тегов, и от тега оставалась скорлупа | Порядок правил зафиксирован: сначала HTML-теги, потом `[…]`; правило ASS применяется дважды (иначе `{\an8}text{\an2}` оставляет «хвост» скобки). `[MUSIC]`/`[Music]` ловятся одним шаблоном `\[[^\]\n]*\]` — регистр для скобок вообще не проверяется, а «спетость» строки определяется символами ♪ ♫ ♬ ♩ 🎵 🎶 ¶ на краю или парной рамкой `# … #` (одиночный `#` — не песня, см. строку про `D18`) |
| **`(GUNSHOT)` и `(together)` удалялись одинаково** | Правило «снимать все круглые скобки» | Круглые скобки снимаются только с ремарки: все токены внутри — заглавные ASCII. Не попадают под правило сокращения (`(No. 5)`, `(Mr.)` — список в `RE_ABBREV_TAIL`) и не-латинские вставки (транслит/перевод, `D8`); `(together)`, `(now!)` сохраняются как речь (`D6`) |
| **`#13-37` превращалось в `13-37`** | Вырезание `#` по всему тексту | `#` — шум только вне цифры и не внутри слова: шаблон `#(?![0-9])`, поэтому `#13-37` и `#hashtag` остаются (`D5`) |
| **Стресс-прогон (`T6.1`) потерял 3 реплики, которых не было в матрице** | `#` считался музыкальным маркером на **любом** краю строки, `\N` (hard break ASS, при экспорте в SRT доезжающий двумя обычными символами) не распознавался вовсе, а бегунок реплики был жёстко `>>` | `#` = «спетая» строка только в парной рамке `# … #` (`RE_HASHTAG_FRAME`), одиночный `#` на краю — шум, который снимается, а строка остаётся (`RE_HASHTAG_NOISE`); литеральный `\N` → перевод строки на шаге 0/1 и склейка как многострочного cue; бегунок — `>+` (`RE_LEADING_DASH`). Матрица §4 пополнена 5 кейсами, регрессия — в фикстуре `stress_realworld.srt` (`D18`) |
| **`UnicodeDecodeError` на не-UTF-8** | Жёсткий `encoding="utf-8"` | Цепочка `FALLBACK_ENCODINGS`: `utf-8-sig` (срезает BOM и для без-BOM файла это валидный utf-8) → `utf-8` → `cp1252` → `cp1251` → `latin-1`; перед цепочкой — chardet, если либа установлена. `cp1252` раньше `cp1251`, потому что корпус английский: для кириллических треков кодировку передают явно (`--encoding`) (T2.1) |
| **`pysrt` ронял импорт всего файла** | На побитых таймкодах pysrt бросает, а на файле «непонятной формы» молча возвращает **ноль** cue | Отказоустойчивость двухуровневая (`D9`): исключение → regex-движок; ноль cue → тоже regex-движок; и только если оба молчат — честная `SubtitleFileError`. Файл не может «успешно» разобраться в 0 реплик (T2.5) |
| **Cue с `end <= start`** | Встречается в реальных rip-ах, в `malformed.srt` — обратный интервал | Форсируется `DEFAULT_CUE_DURATION_MS = 1000`; в БД не попадает ни одна строка с `end_time_ms <= start_time_ms` (T2.3) |
| **Повторный импорт удваивал строки** | `INSERT` без какого-либо условия | `DELETE FROM dialogue_lines WHERE subtitle_id = …` перед вставкой — повтор даёт ровно те же 20 строк, а `line_index` перенумеровывается (`D3`) |
| **`status='processing'` не виделся, `failed` не доживал** | Статус писался в той же транзакции, что откатывалась при ошибке | `processing` коммитится сразу после `FOR UPDATE`-проверки, `failed` — из **отдельного** короткого соединения (`D4`, `D16`) |
| **`UPDATE … rowcount=0` на несуществующем `subtitle_id` → `ForeignKeyViolation`, потом `current transaction is aborted`** | UPDATE без проверки существования | Пред-проверка с `FOR UPDATE` и `SubtitleNotFoundError` до записи (T3.2) |
| **Строки записывались «как в файле», с мусором** | Чистка шла после записи / не шла вовсе | Санитизация **до** записи: в `raw_text` попадает только результат чистки; приёмочный SQL на «грязь» (§6.3) даёт 0 |

## 4. Архитектура и алгоритм

### 4.1. Модули
- **`app/subtitle_parser.py`** (1061 строка) — один self-contained модуль step 2:
  DTO (`DialogueLine`, `ParseReport`, `SanitizerOptions` — `frozen` + `replaced()`),
  санитайзер, оба движка разбора, репозиторий-функции и оркестратор
  `process_subtitle_file(_with_report)`.
- **`app/db.py`** — единственное место соединения: `connection_kwargs()` → `get_connection()`
  → `session()`. Параметры: явные аргументы > `SUBTITLES_DB_HOST/PORT/NAME/USER/PASSWORD/TIMEOUT`
  > дефолты compose.
- **`app/scripts/parse_subtitle.py`** — CLI: `--dry-run` (БД не открывается вообще), `--json`
  (один объект в stdout, логи в stderr), коды возврата `0 / 1 / 2`.
- **`app/README.md`** — как запустить: установка, env-переменные, флаги, тесты, известные ограничения.

### 4.2. Конвейер чистки (`SubtitleSanitizer.clean`, порядок фиксирован)
```
0. управляющие символы → удалены; XML-сущности (&#39;, &quot;, &apos;) → символы;
   типографика (’ → ', … → ...). `&lt;`/`&gt;` в _ENTITY_MAP намеренно НЕТ: их декодирование
   до снятия тегов рисовало бы настоящие теги из текста (D19)
1. <br> → перевод строки; литеральный `\N` (hard break ASS, доезжающий до SRT двумя символами)
   → перевод строки (D18); затем все HTML-теги <…> → удалены
   (теги ДО скобок, иначе <b>[MUSIC]</b> оставило бы пустые <b></b>)
2. ASS/SSA {\…} → пробел, правило применяется дважды («{\an8}text{\an2}» не должно оставить скобку)
3. […] SDH-ремарки → пробел, ЛЮБОГО регистра ([MUSIC], [Music], [door creaks]);
   плюс «висящий» незакрытый [ в хвосте
4. (…) → пробел только если содержимое — ремарка (токены заглавные ASCII, не сокращение вида
   (No. 5), (Mr.)); иначе текст в скобках сохраняется
5..8 построчно: «спетая» строка = нотный глиф на краю (♪ ♫ ♬ ♩ 🎵 🎶 ¶) ИЛИ парная рамка
   «# … #» (`#` не перед цифрой) ⇒ строка выбрасывается (drop_music_lines) или чистится;
   одиночный ведущий/хвостовой `#` — только шум, снимается, строка остаётся (D18);
   внутренние ♪ → пробел;
   метка диктора NAME: / OFFICER 1: / MAN ON TV: / COACH: (апостроф внутри разрешён, чтобы
   «DON'T:» не сжималось в «t»); ведущий/хвостовой дефис реплики (- , — , бегунок >+);
   collapse \s+; строка без букв и цифр → удаляется
9. склейка строк cue (merge_lines ⇒ через пробел) → убрать пробел перед знаками препинания → strip
```
Cue, у которого после чистки осталось пусто, в `dialogue_lines` не попадает вовсе (T2.4):
именно поэтому CHECK на непустой `raw_text` в схеме не нужен (`D17`).

### 4.3. Транзакционный поток записи (шаги a→f из ТЗ)
```
a. require_subtitle (SELECT … FOR UPDATE) + UPDATE subtitles SET status='processing', updated_at=NOW()
   → COMMIT, чтобы «processing» был виден другим сессиям, пока файл разбирается (durable_status=True)
b. decode + parse + sanitize — в памяти, к БД обращений нет
c. DELETE строк этого subtitle_id → INSERT … execute_batch(page_size=500) с переиспользуемым
   cursor/mogrify → COUNT строк; расхождение с числом распарсенных реплик = LineCountMismatchError
d. UPDATE subtitles SET status='parsed', updated_at=NOW()
e. conn.commit()
f. except → conn.rollback() → отдельное соединение для status='failed' → logger.exception → raise
```
`page_size=500` — по одной bulk-вставке на 500 реплик; для эталонного `sdh_full.srt`
это одна страница, `deleted_lines` показывает, сколько строк зачищено перед вставкой.

## 7. Ограничения и следующие шаги

### 7.1. Известные ограничения
1. **`WALTER, JR.: Grandpa?`** — метка диктора с запятой/суффиксом не срезается: регулярка не
   отделяет фамилию с суффиксом от текста. Осознанно оставлено в эталоне (`D15`), правится на
   шаге speaker-моделей.
2. **Четыре опции чистки, три из них во флагах CLI.** `SanitizerOptions` = `merge_lines`,
   `drop_music_lines`, `strip_speaker_labels`, `strip_dialogue_dashes` (`D7`); CLI умеет
   `--keep-line-breaks`, `--keep-music-lines`, `--keep-speaker-labels`. Для `--json`-отчёта
   опции не сериализуются — в статистике виден только итог (`cues_kept/cues_dropped`).
3. **Порог входа по размеру файла.** `MAX_FILE_BYTES = 10 MiB`: файл больше — `SubtitleFileError`
   («обычный `.srt` — ~30 КБ, всё, что выше 10 МБ, — красный флаг»). Отдельного лимита на число
   cue нет; длинный файл режется только пачками вставки (`page_size`).
4. **Миграция 002 написана и проверена, но к живой БД не применена** (решение пользователя).
   `docker/migrations/002_dialogue_lines.sql` (`uq_dialogue_lines_subtitle_index`,
   `chk_dialogue_lines_time_order`) прогнана на одноразовой копии схемы: идемпотентна, констрейны
   работают, боевой прогон парсера поверх копии не ломается (детали — §6.3). Идемпотентность
   импорта обеспечивает приложение (`DELETE` + вставка, `D3`), а констрейны — страховка от
   конкурентных прогонов; применять их или нет — отдельное решение на шаге 3/4.
5. **Оракул «есть буква» в приёмочном SQL неразличим на не-английских строках.** `raw_text !~
   '[A-Za-zÀ-ÿ]'` помечает как грязь легитимный контент (реплика `0`, перевод без латиницы) —
   из-за этого два cue стресс-корпуса переписаны, а сам запрос дополнен проверками 2b/2c/3b
   (§6.3, `D19`/`D20`). Для чисто английского корпуса условие по-прежнему корректно.
6. **Нет per-cue лога дропов.** `ParseReport` даёт только счётчики (`cues_total/kept/dropped`) и
   причину в `drop_reason` у отдельной строки; в CLI-журнале не видно, *какой именно* cue выпал и
   почему. Разбирается по `--keep-*` флагам и фикстурам; если шаг 3 упрётся в это — добавим
   `--verbose-drops`.

### 7.2. Что нужно сделать дальше
Шаг 2 закрыт (`T1.1`–`T6.4`), следующих шагов три:
- **Шаг 3 — разбор лексик** (токенизация/лемматизация `dialogue_lines.raw_text` →
  `episode_word_contexts(line_id, lemma_id, inflected_form)`; справочник `global_lemmas` уже
  наполнен — 10 000 лемм). Окно контекста даёт `idx_dialogue_lines_subtitle_time`
  (`(subtitle_id, start_time_ms)`). Ориентир по объёму работ: в `dialogue_lines` из текстовых
  колонок есть только `raw_text`, многострочные cue в нём уже склеены в одну строку через
  единственный пробел (`SanitizerOptions.merge_lines=True` по умолчанию; литеральный `\N`
  перед этим разворачивается в перевод строки — `D18`), так что токенизатор работает с плоской
  строкой.
  Внимание: `context_translation_ru` и `target_translation_ru` в схеме — `NOT NULL`, то есть
  строка `episode_word_contexts` не появляется без LLM-перевода; это отдельный проект
  (генерация, стоимость, кэш), и его надо спроектировать до первой вставки.
- **Миграция `002_dialogue_lines.sql` — отложена по решению пользователя** (проверена на копии,
  §6.3). Вернуться, когда появятся конкурентные прогоны импорта или импорт из UI: тогда UNIQUE и
  CHECK дешевле применить, чем чинить последствия.
- **`--verbose-drops` в CLI** (см. §7.1 п.6) — по мере надобности: пока дропы разбираются по
  фикстурам и `--keep-*` флагам.
